# Critical Review: crun vs youki Benchmark Signal Validity

**Date:** 2026-05-19
**Branch reviewed:** `main` @ `0ca4c59`
**Scope:** `benches/`, `src/container_runtime.rs`, `.github/workflows/bench*.yml`, `Cargo.toml`

**Verdict: The current benchmarks do NOT produce trustworthy apples-to-apples signal.** Multiple asymmetries in what each backend's `create`/`start` do, environmental noise on GitHub Actions, and broken statistical pipelines mean the reported numbers cannot support a defensible claim about crun-vs-youki latency. Details below.

---

## 1. Apples-to-apples: NO. The two backends do structurally different work per phase.

The `ContainerRuntime` trait splits work into `create` / `start` / `delete`, but the two implementations split that work very differently:

- **`CrunBackend::create`** (`src/container_runtime.rs:121-140`) is essentially a stat() — it only checks that `config.json` exists. No container state is set up.
- **`YoukiBackend::create`** (`src/container_runtime.rs:276-320`) actually builds the container via `ContainerBuilder…build()`, which writes per-container state and (in libcontainer) performs validation work that crun defers.
- **`CrunBackend::start`** (`src/container_runtime.rs:146-185`) shells out to `crun run` — this single command does create + start + delete in one shot (crun spawns, forks, runs to completion, cleans up).
- **`YoukiBackend::start`** (`src/container_runtime.rs:338-377`) calls `Container::load().start()` only; it does **not** wait on the container process the way `crun run` does, and it returns a hard-coded `exit_code = 0i32` (see line 365 with the comment admitting "does not directly return the container process exit code").

Consequences:
- The per-phase microbench (`benches/container_runtime.rs`) compares `create` durations that measure *fundamentally different work* — a file existence check vs full libcontainer build. crun looks artificially fast on `create`; youki looks artificially fast on `start` (because it isn't waiting for the workload to finish).
- `crun/delete` is a literal no-op span emission (`container_runtime.rs:189-200`); `youki/delete` does real libcontainer work (line 384-423). The "delete" column is meaningless.
- Even in the E2E `fork_latency.rs` benches (which sum create+start), the crun path uses `crun run` (subprocess fork+exec+wait), while youki runs `libcontainer` in-process. The "subprocess vs in-process" gap is exactly what the doc-comment on `YoukiBackend` (lines 207-214) cites as *why* the comparison is meaningful — but `crun` also has a separate `crun create` / `crun start` mode that would have been the apples-to-apples choice. The current code uses `crun run` (line 149), so we're measuring "subprocess shell-out + workload" vs "in-process libcontainer call that doesn't wait for workload completion".

**`first_write` partially compensates** by waiting for the sentinel file on disk, but `start()` for youki returns *before* the contained process necessarily exits, so the polling loop (`fork_latency.rs:266-268`) busy-spins until the sentinel appears — including any latency youki incurs to reap the process asynchronously. That's at least directionally honest, but it's measuring different semantics from the crun path where `wait()` already blocked.

## 2. Measurement validity: weak. Criterion is misused as a glorified timer.

- **Sample sizes are tiny.** `fork_latency.rs:290` uses `sample_size(20)` with `measurement_time(30s)`; `first_write` uses 10 samples over 60s (line 344-345). Criterion's minimum sample is 10, and below ~30 the bootstrap CIs are wide and unreliable.
- **The artifact JSON throws away the distribution.** `ForkLatencyResult` records only the *last sample's* duration (`fork_latency.rs:307, 322, 324`: `last_fork_ms`, `last_verified` — overwritten every iteration, written once at the end). Variables literally named `last_*` are then claimed as the result. This is *not* p50/p95/p99; it's a single arbitrary observation. The PR-blocking artifact has zero statistical content. (Compare with `bench.yml:43-49`, which does extract real percentiles — that path uses a different binary entirely.)
- **No warmup discipline.** Each iteration creates a fresh `TempDir`, writes a fresh `config.json`, constructs a fresh `Backend`. The first iteration eats cold-cache I/O, dynamic linker work, page-cache misses for `/usr/bin/crun`, and libcontainer lazy-init. Criterion's normal warmup is disabled by `iter_custom` — you measure cold and warm samples identically.
- **`std::hint::spin_loop` busy-wait (line 267)** burns a CPU on a noisy shared GH runner during the very window we're trying to measure. On a 2-vCPU GH runner this is harmful — you're stealing cycles from the container you're timing.
- **`backend_verified` is racy.** `proc_cmdlines_contain` (lines 208-225) scans `/proc` *after* `backend.delete()` — by then crun has typically already exited. For youki (in-process), no `crun` process should exist anyway, so the check is tautological (`verify_youki_backend` just asserts crun *isn't* running, which is true whenever the bench process itself isn't crun). It is **not** verifying that youki actually did the work.
- **`bench_youki_start` and `bench_crun_start`** (`container_runtime.rs:97-124, 173-202`) include `create` + `start` + `delete` inside the timed closure — so the "start" microbench isn't measuring start at all. That contradicts the doc comment "Measures per-operation latency."

## 3. Environment fairness: poor.

- Runs on `ubuntu-latest` (`bench-container-runtime.yml:31`) — shared, noisy, 2-vCPU. Sub-millisecond comparisons here are not credible.
- The build cache (`bench-container-runtime.yml:62-67`) is keyed on `Cargo.lock` only, not on the feature set. The crun-only run and the `--features youki` run share a cache; that means whichever runs first warms the disk cache for the second. The youki step always runs after crun (lines 80-95 then 86-95), so youki's `start` benefits from warm crun pages and vice-versa for libcontainer — asymmetric.
- Both backends invoke under `sudo` (lines 83, 94, 101, 112). `sudo` itself adds 1-10ms of jitter and PAM overhead to the bench *process startup*, but since it's the parent of criterion, not inside the timed region, this is mainly a noise contributor via cgroup/audit logging.
- **`continue-on-error: true` on the youki steps** (lines 91, 109): if youki silently fails on most iterations, the workflow still passes and publishes JSON. Combined with `backend_available = false` early-exit (`fork_latency.rs:467-470`) accumulating `Duration::from_millis(0)`, a partial youki failure makes youki look *faster*, not slower. This is a silent correctness hole that can mint a false win for youki.
- Toolchain: both backends are built with the same `cargo build --benches` (lines 71-75), so release-vs-debug is consistent — but note neither workflow sets `--release` explicitly. `cargo bench` defaults to the `bench` profile (inherits release optimizations), so this is OK *only* because `Cargo.toml` doesn't override `[profile.bench]`. Worth pinning explicitly.
- Cgroup version, kernel, and seccomp posture on `ubuntu-latest` change with image updates — there is no pinned image SHA, so historical comparisons drift.

## 4. Statistical hygiene: essentially none in the published artifact.

- No CI, no p-values, no outlier removal beyond Criterion's defaults (which only apply to the HTML report, not the JSON artifact).
- Single run on workflow_dispatch — no repetition across runs, no median-of-N-runs.
- The JSON artifact stores `_ms` as `u64` (integer milliseconds, lines 47-48), discarding sub-ms resolution — even though `Instant::now()` measures nanoseconds. For sub-50ms targets in `bench.yml:48`, integer ms truncation is significant.
- No regression detection between commits. Criterion's `--save-baseline` / `--baseline` are unused.

A single CI run **can absolutely** produce a misleading conclusion here, and there's no guardrail that would catch it.

---

## 5. Workload representativeness: thin.

The workload is `/bin/true` or `sh -c 'echo ready > /output/sentinel'` against a busybox-static rootfs. Fine as a startup-overhead probe, but:

- No filesystem I/O of consequence, no syscall mix, no large rootfs traversal — exactly the regime where libcontainer's in-process advantage (no fork+exec of the runtime binary) is maximized. This may **pessimize crun** because crun's subprocess overhead is amortized over zero useful work. Picking a workload with real syscalls (e.g., extract a tarball, compile a hello-world) would shift the ratio dramatically.
- No cgroup, no network namespace, no user namespace in the OCI config (`fork_latency.rs:138-142` only declares `pid` + `mount`). Real fastenv usage almost certainly uses more namespaces; whichever runtime is more efficient at namespace setup is being undertested.

---

## 6. Specific pitfalls observed

- **Youki `start` returns before workload completes** (`container_runtime.rs:354-365`). The `fork_time` measurement in `measure_fork_time` (line 233-246) therefore systematically *under*-reports youki's true cost. crun's `start` blocks via `child.wait()` (line 165-167).
- **Hard-coded `exit_code = 0`** for youki (line 365) — the bench can't detect a workload that crashed inside the youki container. crun-side failures abort the iteration; youki-side failures vanish.
- **`backend_available` short-circuit + `total += Duration::from_millis(0)`** (`fork_latency.rs:469`, 533): inflates iteration count without adding time, dragging the apparent per-iter latency toward zero.
- **`last_*` semantics**: `last_fork_ms` and `last_fw_ms` are whichever value happened to be assigned in the final non-error iteration. If iteration N-1 errored and N succeeded with an outlier, the outlier wins.
- **`bench_crun_delete`** (`container_runtime.rs:126-138`) and `bench_youki_delete` (line 205-221) — crun's is a no-op span emission; youki's loads + deletes a non-existent container ("best-effort, does not return an error"). They are measuring tracing overhead vs libcontainer's load-fail path. Reporting them as comparable "delete latencies" is misleading.
- **First-write polls with no jitter** but `5s` deadline (line 265); on a slow GH runner an outlier iteration can hit the deadline and report 5000ms as a real datum.

## Concrete recommendations

1. **Equalize `create`/`start` semantics.** Either (a) make both backends use the `create`+`start`+`wait` split (crun has `crun create` / `crun start` / wait via `crun spec` state), or (b) only compare the *end-to-end* `fork_time` and stop reporting per-op microbenches that cross-cut very different work.
2. **Make youki `start` block until the container's init process exits** (read PID from state, `waitpid`/pidfd) and return the real exit code. Without this, fork_time on youki is structurally low.
3. **Stop using `last_*` for the artifact.** Collect a `Vec<Duration>` per backend, write p50/p95/p99/min/max/n/stddev to JSON. Criterion's `estimates.json` already contains this — read it from `target/criterion/.../estimates.json` instead of re-inventing.
4. **Move off `ubuntu-latest`.** Use the self-hosted runner that `bench.yml` already targets (`self-hosted, Linux, X64`). Pin CPU governor to `performance`, disable turbo, isolate cores via `taskset`/`cpuset`.
5. **Run N times (≥5), median across runs.** Add a matrix or loop, dump per-run JSON, aggregate. Compare via Mann-Whitney U or Criterion's `--baseline`.
6. **Remove `continue-on-error: true`** on youki steps, or at minimum fail the artifact step when fewer than min-samples succeeded. Currently silent failure can manufacture a youki "win".
7. **Replace `std::hint::spin_loop`** with `std::thread::sleep(Duration::from_micros(50))` so the polling loop doesn't fight the container for CPU on 2-vCPU hosts.
8. **Add a non-trivial workload** alongside `/bin/true` (e.g., busybox `dd if=/dev/zero of=/output/x bs=1M count=10`, or `sh -c 'for i in $(seq 1 1000); do :; done'`). Report both — startup-dominated and workload-dominated regimes.
9. **Drop `bench_*_delete` from comparison reporting** or make crun actually call `crun delete`. As-is it's a tracing-overhead microbench mislabeled as a runtime comparison.
10. **Strengthen identity verification.** `verify_youki_backend` is a tautology. Use a positive signal — e.g., for the youki run, assert `state_tmp/<fork_id>/state.json` exists (libcontainer writes it); for crun, check `/run/crun/<fork_id>` or capture the `--log` output.
11. **Pin the GH runner image** (`runs-on: ubuntu-24.04` and pin via `vmImage` SHA where possible) and the `crun` apt version, otherwise historical bench drift is uninterpretable.
12. **Add `[profile.bench]` to `Cargo.toml`** with explicit `opt-level = 3`, `lto = "thin"`, `codegen-units = 1`, `debug = false` so build mode is reproducible and doesn't depend on Cargo defaults.

## Bottom line

The current pipeline can produce a "crun vs youki" chart, but the chart should not be trusted to within better than ~2x, and the published JSON artifact specifically is **not statistically meaningful** — it records a single last-sample value per backend. Items 1, 2, 3, and 6 above are the minimum changes needed before any conclusion is defensible.
