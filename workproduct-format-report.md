# Default rendering format for user-facing workproducts

**Terminology, defined once, up front.** Two terms already carry fixed meaning in this repo and are avoided below. _Projection_ names (a) Sharp's continuous speculative-merge projection (`crates/sharp/docs/projections.md`) and (b) the brain's existing `/pages/*` HTTP routes, which serve knowledge-base pages "as markdown" straight from `nexum.page_revisions` (`docs/architecture.md`, §HTTP Routes). _Export_ names PRD §9's estate-portability guarantee — the continuously exported git tree and portable schema that let a company leave without a hostage problem. Neither describes what this report is about: the on-demand materialization of one user-facing document — a report, brief, spec, or spec-delta proposal — from md-canonical brain content into a format a human or downstream party can open. This report calls that act a **render**, and its output a **workproduct render**. A render is downstream of both existing "projection" mechanisms and unrelated to "export"; the term is used consistently from here on.

---

## 1. Recommendation

Superfield should default to **self-contained HTML** as the rendering format for user-facing workproducts, with **ODF/OOXML materialized only on demand, at the app template/framework layer**, when a specific workflow needs an editable office-suite artifact — an accountant, auditor, or e-signature counterpart who works in Word, LibreOffice, or Google Docs. This is a two-tier rule, not a single universal format. HTML is the default render for every workproduct a Superfield agent produces: viewed in Studio, embedded in the delivered webapp, or opened directly in a browser. **PDF is generated from that same HTML render** as the terminal, one-way artifact for print, email attachment, and archival/e-signature flows — it is not a competing default, it is HTML's print output. **ODF/OOXML generation is a template-layer capability** an app opts into, mirroring the already-decided move of PDF/DOCX _parsing_ out of core in `docs/rust-reorg-decisions.md` (item 7, tracked as #37) — it is not a core Forge capability and not the default. Markdown remains the storage and interchange layer throughout, unchanged by this decision; the render sits strictly downstream of it, and nothing here alters how content is stored, versioned, or ingested.

**Driver 1 — AI-native document tooling already treats HTML, not ODF/OOXML, as markdown's natural downstream target (confidence: high).** Anthropic's own Artifacts surface lists "Documents (Markdown or plain text)" and "Single-page HTML websites" as distinct, parallel content types, not one subsuming the other, driven by different MIME types and render paths (primary source: [Claude Artifacts documentation](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)). Independently, three actively maintained MCP document-conversion servers built specifically for agent consumption — Docling, Markitdown, Markdownify — all standardize on Markdown as their output format; none offers ODF or OOXML as an export target (corroborating source, blog-quality aggregation: [awesome-mcp-servers](https://github.com/TensorBlock/awesome-mcp-servers/blob/main/docs/knowledge-management--memory.md)). This is directly relevant because Superfield's own agents are LLM-driven and will inherit the format habits of the surrounding tooling ecosystem.

**Driver 2 — Markdown-to-XML materialization is inherently lossy in both directions, and no tooling examined round-trips markdown to ODF/OOXML/HTML5 cleanly (confidence: high).** Pandoc's own manual disclaims lossless conversion between arbitrary format pairs, explicitly noting that formatting details and complex tables "may not fit into pandoc's simple document model" (primary: [Pandoc manual](https://pandoc.org/MANUAL.html)). Tiptap's editor documentation, independently, treats its Markdown extension as "a bridge between Markdown text and Tiptap's JSON document structure" rather than a native representation, and documents concrete losses: inline comments can be dropped on a markdown round-trip, and markdown table syntax cannot represent multiple block-level children within one cell, a construct the richer JSON/HTML model supports (primary: [Tiptap Markdown docs](https://tiptap.dev/docs/editor/markdown)). This claim survived adversarial verification (3-0, 3-0); a stronger, more convenient claim — that Pandoc supports clean bidirectional round-trip between markdown and ODF/OOXML/HTML5 — was checked and refuted 0-3. No format in this comparison should be sold as round-trip-safe.

**Driver 3 — Between the two XML alternatives, OOXML dominates real-world usage while ODF is the more formally standardized spec; both carry real gaps, and neither is a mature target for AI-authored documents today (confidence: medium, partly sourced from an interested party).** ODF is ISO/IEC 26300 (OASIS-developed), while "the vast majority of office documents worldwide use OOXML Transitional" per neutral market-share framing (secondary: [Wikipedia, OpenDocument](https://en.wikipedia.org/wiki/OpenDocument)). The Document Foundation — an ODF-advocacy organization with a direct competitive interest — argues OOXML's structural complexity functions as vendor lock-in; that framing is reported here as one interested party's position, not neutral fact (blog/advocacy: [documentfoundation.org, "ODF vs OOXML"](https://blog.documentfoundation.org/blog/2026/05/28/odf-vs-ooxml-an-issue-that-should-never-have-existed/)). ODF's own round-trip story is also incomplete: tracked-changes behavior is underspecified and implementation-dependent, an active work area still being revised through ODF 1.2→1.3→1.4, with ODF 1.4 only reaching OASIS standard status in December 2025 — recent enough that its real-world support story is not yet settled within this report's 3–7 year horizon. On the tooling side specifically, `python-docx` cannot programmatically create footnotes — an 11-year-old open GitHub issue, still open — while `odfpy` has native, documented footnote-creation support (blog-quality practitioner write-up: [bacsich.org, LLM document generation](https://bacsich.org/wp-content/uploads/2025/11/llm_document_generation_how_odt_and_google_docs_compare_to_word_via_manus.pdf)). This is a narrow tooling fact, not a verdict on either format as a whole, but it directly weakens "generate OOXML because everyone already uses it" as a default strategy.

**Driver 4 — the repo has already made this exact core-vs-template call once, for the input side, and it went the same direction this report recommends for output (my own synthesis from repo grounding, not from web research).** `docs/rust-reorg-decisions.md` records, as a locked decision, that PDF/DOCX _parsers_ are explicitly out of core and move to "template/framework" (#37) — office-XML handling is already precedented as an app-template concern, not a Forge/brain concern. `blueprint/docs/technical/ux-governance.md`, the one existing rendering-format policy anywhere in this repo (for internal UX-review artifacts — a different artifact class, but the same organization making the same kind of format call), states HTML is "preferred for interactive validation," SVG is the static/export format, markdown is a "derived companion," and explicitly warns against duplicating truth across formats. `docs/architecture.md`'s `/pages/*` routes already serve knowledge-base content directly as markdown over HTTP, with no XML office intermediate anywhere in the stack. None of these three facts is about customer-facing workproducts specifically, but together they show that whenever this codebase has made a rendering-format decision, it chose HTML/markdown-native and pushed office-document machinery outward. This driver is weighted heavily because it is the only evidence that is actually about Superfield, rather than the general document-format landscape.

**Driver 5 — PRD §8 and §9 constrain the shape of the render pipeline, even though neither mentions formats directly (my own inference).** PRD §8 states Superfield is explicitly not "a reporting/analytics platform" — "synthesis in service of execution is in scope; reporting and metrics unrelated to the development loop are not." A workproduct render should stay a lean, on-appliance capability in that spirit, not the seed of a BI-style document suite; heavyweight office-document generation is the kind of feature surface a reporting platform builds first, and it argues against making it the default. Separately, PRD §9's sovereignty stance (self-hosted, air-gap-capable, no cloud dependency) does not by itself distinguish HTML from ODF/OOXML — both can be generated self-hosted — but it does penalize any option requiring a cloud conversion API, and it favors a small, well-understood, embeddable toolchain over full docx/odt-generation libraries whose most mature implementations sit in Python or JavaScript ecosystems (Driver 3's python-docx/odfpy evidence), which would sit awkwardly bolted onto Superfield's Rust-core appliance.

## 3. Forward-looking analysis

**User surfaces (confidence: medium-high, mostly sourced projection).** The browser is already the universal renderer for both of Superfield's own surfaces — Studio and the delivered webapp are HTML applications today, not office documents (`docs/technical-requirements.md` §2.10). Independently, AI chat/canvas products (Claude Artifacts) have converged on markdown and self-contained HTML as their two native document-adjacent output types (Driver 1). Projecting forward: the ICP's _internal_ consumption surface (Steerer reviewing an outcome, an Owner reading a gap-surfacing brief) is very likely to keep converging on browser-rendered HTML, because that is where Superfield already lives and where AI-native tooling already lives. The ICP's _external_ consumption surface — an accountant or auditor who has never heard of Superfield — is much less likely to move off office suites in this horizon; those parties are outside Superfield's control and outside the trend this research covers. This is why the recommendation is two-tier rather than single-format: the trajectory argument is strong for the default, and essentially neutral for the escape hatch, which is exactly why the escape hatch is kept rather than eliminated.

**AI generation capability (confidence: medium, explicitly qualified).** Two claims worth separating: current fidelity, and the trend in fidelity. On current fidelity, the evidence in Driver 2 and Driver 3 says plainly that no format in this comparison is confirmed round-trip-safe, and OOXML-generation tooling has at least one documented gap that ODF-generation tooling does not (footnotes). On trend, the mission framing raises a genuinely useful idea that this report treats as **my own forward-looking judgment, not a sourced fact**, because no specific numeric claim about it survived verification (a claim about markdown reducing LLM input tokens by ~33% relative to DOCX/PDF was explicitly refuted 0-3, and a related HTML-token-overhead claim was refuted 1-2 — neither belongs in this report as fact): as frontier models get better at emitting well-formed structured output of _any_ kind, direct generation of valid OOXML or ODF becomes more plausible over the report's 3–7 year horizon, and models increasingly function as on-demand format converters. That capability improvement is a real argument for _keeping the default reversible and cheap to supplement_ (Driver 5, criterion 8), not an argument for choosing ODF/OOXML as the default today. Betting the default on a capability trend that has not yet shown up in the verified evidence would be exactly the kind of unsupported narrative the research explicitly flagged and killed elsewhere (the claim that Anthropic engineers have institutionally moved away from markdown toward HTML was checked and refuted 0-3 — even _that_ directional claim, in HTML's favor, did not survive verification, which is a useful discipline check on how much weight to put on any single trajectory story).

**Tooling ecosystem (confidence: high for what has converged, low for what has not yet happened).** The MCP document-conversion ecosystem (Driver 1) and the general practitioner tooling examined (Pandoc, Tiptap — Driver 2) both treat markdown as canonical and HTML as the natural rich-render target; none treats ODF/OOXML as a first-class target. This is a real, observed convergence today, not a projection. What has _not_ yet happened, despite one source's framing to the contrary: broad, verified cross-suite support for ODF 1.4 across Microsoft Office, Google Docs, and the open-source suites. A claim asserting that support already exists was checked and refuted 0-3 (source: fossforce.com, blog-quality). ODF 1.4 reached OASIS standard status only in December 2025; its practical adoption story is unwritten within this report's horizon and should be tracked, not assumed (see §6).

**Round-trip editability, addressed as an open question (confidence: low, and honestly so).** The research's first open question asks whether Superfield's product actually requires lossless round-trip editing, or whether a workproduct is a generate-and-view/export artifact where one-way rendering fidelity is sufficient. The PRD's approval model is informative here without settling the question outright: approvers judge "behavior demonstrated against representative data... never code diffs" (PRD §5, §9), and the control panel's plain-language risk statement and demonstrated-outcome artifacts are themselves workproduct-shaped — consumed, not edited, by the human making the call. That suggests the _internal_ review-and-approval workproducts lean generate-and-view. But the mission's own product context flags _external_ consumers — accountants, auditors, regulators — as workproduct consumers too, and those parties routinely mark up documents and send them back. This report's honest position: the internal-review workproduct class does not need lossless round-trip; the external-handoff workproduct class probably does need _some_ re-entry path, but neither the PRD nor the architecture docs specify one today, and no format examined in this research offers a confirmed lossless path in either direction. The architecture sketch below treats this as a real, unresolved seam rather than papering over it with an assumed format fix.

## 4. Architecture sketch

**Layers.** `md-canonical brain (Nexum)` → `render pipeline (new capability)` → `surface (Studio HTML / delivered webapp HTML / email attachment / on-demand office document)`.

- **Brain (core, unchanged).** Workproduct source content is markdown, stored the same way knowledge-base pages already are: `nexum.page_revisions` (append-only, `workspace_id` + `page_name` + `content`), reachable today via `GET /pages/{name}` and `superfield page <name>` (`docs/architecture.md`, §HTTP Routes, §Known page names). This report changes nothing about storage, versioning, or ingestion.

- **Render pipeline (new capability, template/framework layer).** This is the layer this report is actually about, and it does not exist yet in any form (`docs/technical-requirements.md` §3 lists it under "not yet existing in any form" only implicitly, via the app platform §2.9). It belongs in the app-template scaffold, not core, for the same reason PDF/DOCX _parsing_ was already moved there (#37): it is workflow-specific machinery an app opts into, structured the same way `sf-connector` is scoped per workspace with a closed capability set (`docs/architecture.md`, §Systems-of-Record Connector Seam) rather than a global core dependency. Concretely: an HTML template/render step (default, small, Rust-embeddable or a thin templating layer) produces the workproduct render from markdown content; a headless-print step turns that same HTML into PDF for the terminal/print/archival/e-signature case; an optional, per-app ODF/OOXML exporter is available as a template-layer dependency, gated per workspace the same way connector credentials are, and invoked only when a specific workflow calls for an editable office artifact.

- **A concrete near-term gap this closes, worth flagging explicitly.** Today, `/pages/*` returns raw markdown text, not an HTML page — there is currently no server-side step anywhere in the stack that turns `nexum.page_revisions` content into something a human opens directly in a browser without a client-side renderer. The render capability recommended here would close that existing gap as a side effect, not just serve a hypothetical future "workproducts" feature; it is additive to a concrete hole in the current architecture, not a purely speculative build.

- **Surfaces.** Studio and the delivered webapp already are HTML surfaces (`docs/technical-requirements.md` §2.10); a workproduct render is embedded or linked the same way any other Studio content is. The PDF terminal render is what leaves the appliance as an email attachment or e-signature input. The on-demand ODF/OOXML render is what leaves the appliance when a specific downstream party needs an editable office document.

- **Round trip, stated honestly.** Two paths, not one. (a) _In-brain editing_: if an app embeds a rich-text/markdown editor over the HTML render (the same bridge pattern Tiptap's own documentation describes — HTML/JSON model on one side, markdown on the other, with documented, bounded loss), edits can post back into the brain through the existing ingest path (`/studio/docs`, `crates/sf-serve/src/routes/ingest.rs`) as a new markdown revision. This is the well-understood, already-precedented path, and it is where this report expects most human-initiated corrections to actually happen. (b) _Out-of-brain editing_: once a render leaves the appliance as PDF or an office document, it is one-way. An edited copy re-enters only through structured re-ingest — an attachment upload plus agent-assisted diff/merge back into markdown — not automatic sync. This is a real limitation, not a rounding error, and it is listed again in §6 as something to watch rather than something this report claims to have solved.

## 5. Rejected alternatives

**ODF/OOXML as the default, rather than the on-demand exception.** Rejected on the weight of Drivers 1–5: neither format is where AI-native surfaces are heading; no format examined is confirmed round-trip-safe and OOXML-generation tooling has at least one documented, long-standing gap; a docx/odt toolchain would pull a heavier, non-Rust-native dependency into or near core, in tension with the already-locked #37 decision to keep this machinery in the template layer; and static office-XML documents have no path to the interactive/embedded-data-viz ceiling that Studio and the delivered webapp already assume as HTML surfaces. ODF/OOXML is not eliminated — it remains available, on demand, at the template layer, which is the one criterion (downstream interop for editable-office-document workflows) where it is genuinely the stronger candidate.

**PDF as the default, rather than a derived terminal render.** Rejected because PDF has no live round-trip path at all and Studio/the delivered webapp are already HTML surfaces — making PDF the default would mean rendering a second time for every screen view. Instead, PDF is adopted as the print/archival/e-signature terminal render, generated from the same HTML the default already produces, so it costs no separate template or generation path.

**A Typst/LaTeX pipeline, as a secondary candidate.** Considered per the mission's allowance for secondary candidates and rejected as not materially changing the recommendation. Typst is reported to compile faster and use cleaner syntax than LaTeX (blog-quality practitioner source: [slhck.info, "Typst PDF Generation"](https://slhck.info/software/2025/10/25/typst-pdf-generation-xelatex-alternative.html)), but that benefit targets technical/academic typesetting users producing print-quality documents from markup by hand — not Superfield's ICP of non-technical executives and a sysadmin-generalist operator, and not a workflow where an agent is already generating HTML. Adding a Typst toolchain would introduce a new language/runtime dependency to solve a print-quality problem the HTML→PDF terminal render already solves adequately for this product's needs.

**Serving raw markdown directly to end users, as a "neither" position.** The mission spec allows evaluating "md-with-render-pipeline" as a genuine third position; in practice the recommendation above already _is_ a render pipeline over markdown, so this is less a rejected alternative than a clarification of what was rejected: shipping the `.md` file itself as the workproduct, the way `/pages/*` already does for internal knowledge-base pages. That remains fine for developer- and agent-facing content, but it is rejected as the default for customer-facing workproducts: non-technical executives, accountants, and auditors are not markdown's audience, raw markdown carries no rich formatting or embedded data viz, and it is a weaker first impression for a paid on-prem appliance's non-technical buyer than a rendered page.

## 6. Risks and revisit triggers

- **Trigger — verified frontier-model OOXML/ODF fidelity.** If frontier models demonstrate reliable, CI-verified first-pass valid OOXML or ODF generation (a concrete bar: >99% first-pass validity across a representative document corpus, independently verified, not vendor-claimed) without a template library, Driver 2's cost objection weakens substantially. This would not automatically flip the _default_ — the trajectory, interface-ceiling, and operational-cost criteria are independent of generation fidelity — but it would justify re-evaluating whether office-XML generation belongs closer to core rather than staying template-layer-only.

- **Trigger — ICP telemetry shows office documents dominate real handoffs.** If usage data or a customer survey shows a large majority of workproduct approvals or downstream handoffs happen through editable Office documents rather than viewing in Studio/the webapp or a PDF, that is direct evidence against the trajectory argument in Driver 1 for _this specific customer base_, and would justify promoting ODF/OOXML from on-demand to default for the affected workproduct types (not necessarily all of them).

- **Trigger — ODF 1.4 achieves independently verified broad support.** ODF 1.4 reached OASIS standard status in December 2025; a claim that it is already broadly supported across Microsoft Office, Google Docs, and the open-source suites was checked in this research and refuted (0-3, blog-quality source). If independent, non-advocacy sources later confirm that support materialized within the horizon, ODF's round-trip and interoperability story improves materially and the comparison in §2 should be re-scored.

- **Trigger — a genuine collaborative round-trip requirement surfaces.** The forward-looking analysis in §3 treats round-trip editability as an open, honestly-unresolved question. If a customer segment turns out to need collaborative track-changes editing that must feed back losslessly into the brain — rather than the generate-and-view pattern this report assumes for most workproducts — the architecture sketch's two-path round-trip model in §4 needs to be re-derived, and the format comparison in §2 (criterion 4) should be re-weighted, since neither HTML nor ODF/OOXML currently offers a confirmed lossless path.

- **Trigger — markdown's structural ceiling causes real information loss.** Driver 2 documents, from primary sources, that markdown cannot represent multi-block table cells and can silently drop comments on round-trip. If a Superfield workproduct type (e.g., a financial table with nested structure) hits this ceiling in practice, the fix is a brain **schema** change to carry richer block structure — not a render-format change — and should be scoped and tracked separately from this decision.

- **Note on framing, not a trigger.** The research's fourth open question asked whether the repo's canonical docs already imply or foreclose a format choice. They do not foreclose one — there is no existing ADR on this topic, which is why this report exists — but Driver 4 shows they do lean, consistently, toward the recommendation made here. That lean is evidence, not a settled decision; this report is the input to the ADR that would settle it.

## 7. Suggested ADR skeleton

**File:** `docs/adr-workproduct-formats.md`
**Title:** Default rendering format for user-facing workproducts
**Status:** Proposed

**Context.** Superfield's storage and interchange layer is markdown-canonical (Nexum, `nexum.page_revisions`). No decision exists today for how a workproduct — a report, brief, spec, or spec-delta proposal — is rendered for a human or a downstream party to consume. Two lead candidates were evaluated: self-contained HTML, and open-document XML (ODF/OOXML). Full evaluation, evidence, and citations: see the underlying research report (this document).

**Decision.** Self-contained HTML is the default render for user-facing workproducts. PDF, generated from the same HTML render, is the terminal render for print, email attachment, and archival/e-signature use. ODF/OOXML generation is an on-demand, per-app capability at the template/framework layer (consistent with the existing decision in `docs/rust-reorg-decisions.md` moving PDF/DOCX parsers out of core, #37) — not a core Forge capability, not the default.

**Consequences.**

- _Positive:_ the render pipeline stays small, self-hosted, and Rust-native-compatible; it reuses Studio's and the delivered webapp's existing HTML surface rather than adding a parallel document format; it closes an existing gap (`/pages/*` currently returns raw markdown, not a rendered page); it keeps the default cheap to supplement later (template-layer ODF/OOXML export can be added per-app without a core or schema change).
- _Negative:_ editable-office-document handoffs (the literal "send it to my accountant" case) require an explicit template-layer opt-in rather than working out of the box; round-trip editing of anything that leaves the appliance as PDF or an office document remains a one-way, re-ingest-required path, not an automatic sync — a real, currently-unsolved limitation.
- _Deferred:_ whether any workproduct type needs collaborative, lossless round-trip editing (open question, §3/§6); whether markdown's structural ceiling (multi-block table cells, comment loss) requires a brain schema extension for specific workproduct types (§6).

**Alternatives considered:** ODF/OOXML as default (rejected, §5); PDF as default (rejected, §5); Typst/LaTeX pipeline (rejected, §5); raw markdown as the customer-facing workproduct (rejected, §5).

**Revisit triggers:** see §6 — verified frontier-model office-XML fidelity; ICP telemetry showing office-document-dominant handoffs; independently verified broad ODF 1.4 support; a confirmed collaborative round-trip requirement; observed markdown structural-ceiling data loss in a real workproduct.
